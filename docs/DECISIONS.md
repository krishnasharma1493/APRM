| D59 | A job added mid-run with arrival = now (answers O-13; decided autonomously, to review). **Yes, there is a second selection step at the same tick.** A job added with arrival equal to the current time is an ordinary pending job. The next `sim_step` finds that its arrival time equals `now`, so it handles time `now` again: no finish is left at that time, the job joins the waiting heap, and the greedy-fill selection step runs again. The clock never moves backwards and does not advance for such a step; `sim_add_job` still rejects arrival < `now` with `ARRIVAL_IN_PAST`. `sim_run_until(t)` does not move the clock to `t`: `now` stays at the last event handled, so a job can still be added at any arrival >= `now`. **Determinism rule:** for any workload, adding all jobs first and adding each job mid-run give identical schedules whenever every job is added before the `sim_step` that handles its arrival time (tested on 1,000 random workloads against a tick-by-tick reference). **Edge case:** if a job is added after the step for its own arrival time has already run (only possible when arrival = `now`), it sees the machine as the first pass left it: jobs that were already started stay started, so a lower-id job added late cannot take the place of a higher-id job that started a moment earlier. The schedule can then differ from the add-all-first schedule, but it is still fully determined by the order of API calls, and the late job is never lost or started before its arrival. This edge case will be the normal case for the website's mid-run "add job at the current time"; only the initial load (all jobs added before the first step) avoids it, so K-25 must tell the user or default new jobs to a later arrival. `sim_run_until(t)` leaves `now` at the last event it handled, not at `t` | Simplest rule: no special case in `sim_step` or `sim_add_job`, no new state, the engine just processes the earliest event time at or after `now`; keeps the clock monotone; deterministic from the call sequence | Defer the late job to `now + 1` (changes its arrival, breaks the output columns); reject arrival = `now` after a step (the user could never add a job "right now"); re-run selection inside `sim_add_job` (selection would happen outside `sim_step`, hiding it from the step log and the invariant check) | K-09 (proposal in issue #10) |
| D60 | Event log (answers O-7; decided autonomously, to review). **(1) `PROMOTE_INFO` is reserved and never emitted**, like `REJECT` (D54): the enum value and its place in the PRD §5 kind list stay, and `eventlog_format` has a placeholder sentence for it. Reason: aging keeps a fixed key `1000·b − alpha_milli·r` and nobody is ever "promoted" at a moment in time, and a reservation already has its own kind (`RESERVE`), so no engine decision needs a separate informational kind; a later issue may give it a meaning by amending this entry. PRD §5 now says so. **(2) Storage.** An entry stores numbers, not text: `{seq, t, job, kind, a[4]}` (56 bytes); the sentence is built with `snprintf` when asked for (`eventlog_format`, called while writing the JSON) into a 256-byte buffer, cut safely if the caller's buffer is smaller (always NUL-terminated, returns the stored length, sentences are ASCII so a cut cannot split a character); numbers are `int64` printed with `%lld`, no floating point. `seq` = index + 1, starts at 1, restarts at 1 on `sim_reset` (the buffer is kept, so reset cannot fail). `since_seq` returns entries with `seq > since_seq` (<= 0: all; at or beyond the last: `[]`). **(3) Emitted by `sim_step`:** per step, in this order, `FINISH` for each job ending (finish time, then arrival, then id: the finished-list order), `ARRIVE` for each job joining the waiting heap (arrival, then id), then in greedy-fill order one `START` or one `SKIP` per waiting job popped. `START` and `SKIP` report the free CPU and memory just before the decision. `RESERVE`, `BACKFILL` (K-26) and `BATCH_SELECT` (K-34) have formatters and tests only. **(4) Sentences:** `Job 9 arrived with priority 2.` / `Job 3 started: needs 8 cores and 4096 MB; 8 cores and 28672 MB free.` / `Job 7 skipped: needs 20480 MB, only 8192 MB free.` (names only the short resource: `needs 2 cores, only 1 core free.`; both short: `needs 2 cores and 300 MB, only 1 core and 200 MB free.`) / `Job 3 finished after 25 ticks; freed 8 cores and 4096 MB.` / `Job 3 reserved: start guaranteed at t=55.` / `Job 9 backfilled: finishes at t=50, before the reservation at t=55.` / `Job 4 chosen for the best batch of 3 jobs.`; "1 core", "1 tick", "1 job" are singular. **(5) SKIP volume.** A SKIP is logged for a waiting job the first time the greedy fill cannot start it, and again only when its set of short resources changes (mask = cpu short | memory short << 1: cpu only, memory only, both). The mask is stored in the waiting entry (`WaitEntry.skipmask`, 0 at ARRIVE; it is not part of the ordering) and the SKIP sentence is built from the numbers at the moment of the change, so no information is dropped silently: an unchanged reason is already on the log. The loop still stops when free CPU or memory is 0, so jobs behind that point are not examined and get no SKIP. This replaces the first idea (one SKIP per examined job per event), which on a legal 5,000-job workload (5,000 big-memory jobs queued behind a running hog) wrote 12.5M-25M entries (0.7-1.4 GB) and would crash the WebAssembly build. Bound: a job's SKIPs are at most the number of events at which its mask changes (at most one per event). In the hog case that is one each (2,000 queued jobs give 8,002 entries in total); on 1,000 random small workloads the most for one job was 13, because free resources can rise and fall so the mask can alternate.
